# HANI-EL GOLD — برنامه تکمیل روی Staging (بدون خرید دامنه)

## مرزهای مهم
- آدرس فعلی: https://haniel-gold.pages.dev — فرانت‌اند روی Cloudflare Pages.
- Cloudflare Pages **سرور Django/PostgreSQL اجرا نمی‌کند**؛ تغییر ظاهر/تعامل‌ها و ساخت استاتیک مستقل است.
- Django Admin موجود و APIهای واقعی باید روی یک runtime مستقل و امن با PostgreSQL راه‌اندازی شوند.
- در Staging هیچ پرداخت واقعی، فروش قطعی، پیامک واقعی یا قیمت نامعتبر نباید فعال باشد.
- اختلال دسترسی کاربران ایران به pages.dev گزارش شده؛ از آن به عنوان محیط توسعه استفاده می‌کنیم، نه دامنه فروش.

## هدف پایان فاز Staging
1. UI/UX موبایل/دسکتاپ: هدر، منو، دسته‌بندی، مجموعه‌ها، محصول، جست‌وجو، علاقه‌مندی‌ها، سبد و فرم‌ها.
2. پنل مدیریت فارسی Django با لوگوی رسمی، افزودن/ویرایش کالا، دسته‌بندی، تصاویر، وزن، عیار، اجرت، سود و موجودی.
3. محاسبه فقط سمت سرور: نرخ معتبر ۱۸ عیار Servix، کنترل زمان/واحد، Decimal، مالیات و سیاست تأییدشده.
4. کاتالوگ واقعی: نمایش کالا و قیمت فقط از API (نه مقدار فرضی)، تاریخ نرخ، حالت نبود/قدیمی‌شدن نرخ.
5. ورود OTP با ارائه‌دهنده SMS.ir در محیط تست/سندباکس در صورت فراهم بودن؛ جلوگیری از Abuse، عدم انتشار کلید.
6. گردش سفارش/پرداخت در تست، با تأیید idempotency/رزرو و بدون درگاه واقعی تا زمان مجوز راه‌اندازی.
7. SEO، سرعت، تصاویر، دسترس‌پذیری، موبایل RTL، پایش، هشدارها، امنیت و تهیه/بازگردانی بکاپ.
8. CI سبز و تست عملی end-to-end روی PostgreSQL و HTTPS.

## معماری پیشنهادی تا هنگام خرید هاست اصلی
- Cloudflare Pages: همان فرانت فعلی و آدرس pages.dev.
- Django + PostgreSQL: محیط Staging مستقل و کم‌هزینه/با اعتبار آزمایشی (مثلاً AWS که مالک از پیش حساب اعتباری دارد؛ **فقط با تأیید مالک**).
- همان داده، مدل و منطق Django برای production حفظ شوند؛ **D1 یا Workers به‌عنوان بک‌اند فروشگاه دوم ساخته نشوند**.
- دسترسی ادمین فقط از HTTPS همراه احراز هویت/محدودسازی دسترسی؛ برای Staging در صورت امکان Cloudflare Access یا محدودیت شبکه.
- در صورت استفاده از دامنه متفاوت برای API باید CORS، CSRF، Session Cookie، SameSite/Secure و نگهداری رسانه‌ها با تست واقعی بازبینی شوند.
- ترجیح آینده: proxy امن same-origin `/api` با Cloudflare Pages Functions یا استفاده از دامنه تست API؛ قبل از روشن شدن این مسیر، وضعیت دمو فرانت نباید تغییر کند.
- نرخ Servix، SMS.ir و هر راز فقط در محیط سرور نگهداری شود؛ **هرگز** در Cloudflare Pages build یا GitHub عمومی.

## راهنمای فازهای اجرایی
**فاز A — اکنون:** پولیش فرم‌های Django Admin، اسناد و CI، تکمیل UX و حالت‌های خالی/خطا بدون قیمت ساختگی.  
**فاز B — نیازمند سرور Staging:** Docker/PostgreSQL، migrations، createsuperuser، HTTPS، media، اتصال فرانت به API و تست CRUD واقعی کالاها.  
**فاز C — پس از ورود کلیدها:** Servix، SMS.ir و تست دقیق واحد، زمان نرخ، ارسال OTP، محدودیت‌ها و خطاهای قطع سرویس.  
**فاز D — قبل از انتشار نهایی:** قیمت‌گذاری تأییدشده مالی، تصاویر کالاهای واقعی، مجوزها، درگاه، سفارش آزمایشی واقعی، بکاپ و انتقال به هاست داخل ایران با دامنه شخصی.

## معیار پذیرش
- کاتالوگ بعد از ویرایش ادمین **واقعاً برای همه بازدیدکنندگان** تغییر کند؛ localStorage شخصی مرورگر جای دیتابیس نیست.
- ساخت/ویرایش وزن یا اجرت در Admin در قیمت تأییدشده API منعکس شود؛ قیمت محصول دستی وارد نشود.
- خطای سرویس نرخ نباید به فروش با قیمت قدیمی منجر شود؛ در UI زمان و اعتبار روشن باشد.
- هر عملکردی که هنوز به سرویس خارجی وصل نشده باید به وضوح غیرفعال باشد.
- ارتباط Pages با backend Staging بدون افشای راز و مطابق قوانین امنیتی HTTP/HTTPS آزمایش شده باشد.
- خروجی CI و تست‌های Integration/E2E مستند باشند؛ Staging موفق را معادل Production Ready ندانیم.

## گام بعد برای کار روی همین Staging
برای اینکه پنل واقعی `/admin/` و PostgreSQL کار کنند، لازم است مالک انتخاب و اجازه دهد یک سرور آزمایشی با اعتبار AWS موجود یا یک سرویس اقتصادی جداگانه راه‌اندازی شود. تا پیش از آن، می‌توان رابط و API را توسعه و با تست‌های CI اعتبارسنجی کرد، اما نمی‌توان تغییرات ادمین را در Cloudflare Pages استاتیک برای همه کاربران ذخیره کرد.
